# Memory Mechanism: Regional Coverage And Relay Constellation

## Summary

This rewrite is grounded in the exported OpenCode + DeepSeek V4 Pro traces for the memory-accumulation experiment. I inspected the memory-conditioned opencode SQLite traces, agent stdout, verifier outputs, run metadata, and final verifier metrics for Regional Coverage and Relay Constellation under Codex memory and own memory. The no-memory baseline traces are not present under the memory-accumulation root; the corresponding OpenCode + DeepSeek V4 Pro baseline traces are exported under the main-agentic matrix and match the no-memory aggregate rows, so this report uses those traces as the no-memory control instead of treating aggregate tables as mechanism evidence.

Memory transfers more than the written procedures used in the skill-injection condition. The trace-level difference is that the space agent reads notes from previous runs and reuses concrete solver habits: exact or approximate candidate generation recipes, verifier-backed thresholds, orbit-family parameters, per-sample routing abstractions, and known failure patterns. That transfer is high variance. It can turn a weak regional search into a broad candidate-selection run, or turn a zero-service relay case into full service; it can also import a case-mismatched geometry prior, overfit to a previous stopping rule, or preserve a partial-service relay abstraction that is worse than the no-memory baseline on the current case.

## Regional Coverage Trace Evidence

The clearest DeepSeek Regional case where memory changes search breadth and candidate selection is Codex-memory `case_0002`. The no-memory baseline for the same case ends valid with 15 actions and WCR 0.2691. In the Codex-memory trace, row 10 lists a memory directory, row 21 reads the regional strip note, and the note itself contains prior verified WCR 0.9235 plus a recipe for using verifier geometry, coarse centerline windows, top exact candidates per region/satellite/window cluster, greedy exact selection, and local swaps. The subsequent trace does not simply copy a solution; it tries to operationalize the recipe for the current case. Row 276 runs a solver that reports 193 coarse windows for black_sea and prints the satellite roll limits and candidate-generation settings. Row 287 records that the verifier accepts the solution and reports WCR 0.8832 with 64 actions; row 409 preserves that incumbent as the final task result. This is stronger than an action-count argument: the trace shows memory changing the candidate-generation workflow before the final 64-action selection.

Codex memory also exposes the boundary. In `case_0003`, the trace again reads the memory directory at row 10 and the regional note at row 20, then reads an AEOSSP note at row 26. It uses the remembered lesson that a verifier or exact geometry should guide search, but the run repeatedly spends effort on extraction, private propagation, and black-box verifier handling. The final run metadata is valid but has zero actions and WCR 0.0. That regression is important: the memory note transferred a workflow aspiration, but the agent failed to instantiate the previous candidate family in the current geometry before handoff.

Own memory gives a second Regional example with more same-system transfer. In own-memory `case_0003`, row 15 reads an OpenCode-authored regional note that is less elegant than the Codex note but highly actionable: subsample the coverage grid, generate candidate strips, keep only covering actions using verifier feedback, sort by duration, prune non-covering strips, and avoid over-blacklisting. The trace follows that recipe. Rows 163-181 verify several candidate files, restore a valid high-coverage incumbent, and rows 185-190 remove one non-covering action to reach a clean valid 59-action solution with WCR 0.8060. Row 198 then runs a fill solver that generates 17,370 candidates and a 396-candidate feasible pool but finds no further improvement. The final answer is not merely "more actions"; it is a remembered candidate-selection loop with verifier-backed cleanup.

## Relay Constellation Trace Evidence

Codex-memory `case_0003` is the useful Relay transfer case. The no-memory baseline for this case is valid but has service 0.0 despite eight added satellites. The Codex-memory trace reads the relay note at row 20; the note records a prior six-satellite Walker-like family, altitude about 1,202 km, inclination about 73.65 degrees, and a workflow based on exact demanded-sample scoring and max-link handling. The trace then shows a multi-round implementation of that prior. Early private solvers estimate full service but fail verifier checks: row 276 diagnoses geometric infeasibility and max-link violations, rows 280-304 isolate degree-constraint problems around active links, and rows 305-317 repair path selection by blacklisting or retrying paths that violate degree constraints. Row 317 finally verifies a valid solution with service 1.0 and worst-demand service 1.0. The final run metadata confirms 6 added satellites, 70 ground-link actions, 30 ISL actions, and all five demanded windows served fully.

That useful transfer is not just a design prior; it is design plus scheduling abstraction. The memory provided the orbit family, but the trace only succeeds after the agent builds a per-sample routing and degree-constraint loop. This explains why memory can help Relay more than written procedures in some cases: the note supplies a tested constellation family and a concrete repair agenda for verifier failures, while the live run still has to make link activation intervals and endpoint/satellite degrees agree with the current demand windows.

The Relay regression evidence is equally concrete. In Codex-memory `case_0001`, row 19 reads the same relay memory note and the trace begins with the same high-level design idea, but final run metadata records service 0.1852 and worst-demand service 0.0 with six added satellites. The no-memory baseline for this case is much stronger: service 0.9222, worst-demand service 0.5333, and six added satellites. The same prior that solved `case_0003` badly mismatches `case_0001`; memory transferred a constellation habit without the case-specific path allocation needed to protect worst-demand service.

Own-memory Relay shows a different transfer channel. In `case_0002`, the trace reads `relay-constellation-run-notes.md` at row 15. The note emphasizes source endpoint to source satellite to optional ISLs to destination satellite to destination endpoint, simultaneous sample intersections, and endpoint capacity constraints. The trace then builds per-sample link selection, and row 301 verifies a valid 31-action solution with service 0.7734 before later refinement reaches service 0.9635 and worst-demand service 0.8444. In `case_0004`, however, the same memory style regresses. Row 18 reads the relay note, rows 175-204 analyze backbone planes, ground visibility, and ISL connectivity, and rows 389-410 compare backbone-only versus four added bridge satellites. The final verified solution at rows 422-443 is valid with service 0.7037, worst-demand service 0.3067, and four added satellites. No-memory on the same case is service 0.9222 and worst-demand service 0.6000. The trace did real work, but the selected bridge-relay prior left the current worst demand under-served.

## Boundary Note

The memory regressions are not generic noise; they identify the mechanism. Memory transfers priors and habits, not guaranteed objective alignment. A previous Regional note can transfer candidate-generation structure but still fail if the current run never instantiates productive strips before handoff, as Codex-memory `case_0003` shows. A previous Relay note can transfer a Walker-like constellation or bridge-relay idea but still lose to no-memory if the current case needs different demand-window prioritization, endpoint allocation, or worst-demand balancing, as Codex-memory `case_0001` and own-memory `case_0004` show. The safe claim is selective empirical transfer under matched structure, not that memory is generally superior to static skills or baseline search.

## Paper-Ready Explanation

Agent-derived memory helps solution construction when it carries empirical search knowledge that written procedures do not contain: which candidate families were worth trying, which verifier-backed thresholds mattered, and which failure repairs were necessary in previous runs. In Regional Coverage, memory can broaden candidate generation and preserve high-coverage incumbents; in Relay Constellation, it can transfer a tested relay-design and per-sample scheduling abstraction. The same traces also show the boundary: remembered priors can regress when the current case requires different demand-window prioritization or when the run preserves the prior without rebuilding objective-aligned search.
