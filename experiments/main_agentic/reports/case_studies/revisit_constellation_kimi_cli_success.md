# Kimi CLI on Revisit Constellation

This case study diagnoses why `kimi_cli` performed unusually well on `revisit_constellation`, surpassing the recorded solver baseline mean in the `main_agentic` report. The evidence is anchored to tracked artifacts: aggregate results in `experiments/main_agentic/reports/revisit_constellation.md`, solver baseline rows in `experiments/main_solver/README.md`, the exposed workspace contract in `experiments/_fragments/prompts/revisit_constellation/README.default.md`, scoring code in `experiments/_shared/score_normalization.py`, and Kimi trace exports under `experiments/main_agentic/reports/traces/data/events/revisit_constellation__kimi_cli__test__case_000*.js`.

## Outcome

The headline is real but easy to misread. Kimi's `main_agentic` mean normalized score is 73.36, above the strongest recorded solver baseline mean from `revisit_constellation_j2_rgt_set_cover`, which is about 70.98 under the same normalization. Kimi did not dominate every case. It lost case 0001 to the J2 set-cover baseline because its final capped gap was 6.1784 h instead of the 6 h floor, tied case 0003 on the primary and secondary metrics, and lost case 0004 because the baseline reached the 8 h floor with 15 satellites while the submitted Kimi artifact used 18. The mean win comes mainly from case 0002, where Kimi reached the 8 h floor with 8 satellites instead of 15, and case 0005, where it reached the 6 h floor with 12 satellites instead of 20. That is not a loophole in the benchmark: after the mission revisit requirement is met, fewer satellites are exactly the real-world cost and architecture pressure the task is meant to expose.

| `case_0001` | valid, 14 sats, capped gap 6.1784 h, normalized 69.41 | valid, 16 sats, capped gap 6 h, normalized 71.33 | Kimi saved satellites but missed the revisit floor, so it lost the 70-point gate. |

## Contract Discipline

Kimi's success begins with unusually good authority discipline for this benchmark. Across all five traces it reads `/app/workspace/README.md`, reads or checks the Brahe skill/environment, and uses the packaged verifier as an acceptance oracle. The direct trace counts are: case 0001 reads README at seq 8, Brahe skill at seq 18, verifier help at seq 30, and runs the verifier eight times; case 0002 reads README at seq 8, Brahe skill at seq 28, and runs the verifier twelve times; case 0003 reads README at seq 8, Brahe skill at seq 32, and runs the verifier seven times; case 0004 reads README at seq 24, verifier help at seq 25, Brahe skill at seq 32, and runs the verifier eighteen times; case 0005 reads verifier help at seq 8, README at seq 24, Brahe skill at seq 34, and later embeds verifier calls inside generated scripts.

That matters because the revisit README is almost a solver specification. It tells the space agent the exact solution schema, GCRF state convention, J2 propagation expectation, sampled visibility checks, slew formula, battery model, revisit-gap definition, and the ranking rule: drive capped revisit gaps down first, then use fewer satellites once revisit targets are met. Kimi does write private propagation, geometry, and scheduling code, but in these traces that code is mostly a candidate generator. When the verifier rejects a candidate or reports a weaker metric, Kimi typically changes the model, adds safety margins, or searches a different constellation rather than declaring the private model correct.

## What Kimi Built

Kimi converges on a pragmatic solver family: Walker-like or near-Walker constellations, usually circular orbits inside the altitude bounds; access-window generation using Brahe or J2-aware propagation plus ECI/ECEF geometry; local filters for elevation, slant range, off-nadir, duration, overlap, and approximate slew feasibility; and a greedy or priority-style scheduler that tries to fill each target's revisit timeline. It then wraps that solver in a small parameter search over satellite count, plane count, inclination, altitude, margin, and phase offsets.

The traces show repeated "model then verify" loops. In case 0002, Kimi starts with larger constellations that already meet the 8 h floor, then reduces satellite count: valid 20, 16, 15, 12, 11, 10, 9, and finally 8 satellites, with final verifier output at seq 919 reporting `is_valid: true`, `capped_max_revisit_gap_hours: 8.0`, `num_satellites: 8`. It then investigates 7-satellite removals and random 7-satellite designs, notices target coverage holes, and keeps the verified 8-satellite file. In case 0005, Kimi first finds a valid 14-satellite 6 h solution, then notices a 12-satellite design is only slightly above the threshold, runs a random phasing search, and at seq 644 finds a verified 12-satellite solution with `capped_max_revisit_gap_hours: 6.0` and `max_revisit_gap_hours: 5.980555555555555`.

The pattern is not perfect. Case 0001 reaches a verified 15-satellite 6 h solution inside the trace, but the aggregate final artifact is 14 satellites with capped gap 6.1784 h. The trace tail shows Kimi trying a 14-satellite random search after producing a solid 15-satellite file; the background task times out, and the final collected artifact appears to be a weaker 14-satellite attempt. Case 0004 similarly finds verified 17-satellite variants at seq 505 and seq 506, and even a near-miss 16-satellite variant at seq 546 with one target at 8.0056 h, but the aggregate row reports an 18-satellite final artifact. The most likely explanation is mundane but revealing: Kimi generated and verified better side files, such as `solution_17_5_750_98.json`, then did not copy the best candidate back to the canonical `/app/workspace/solution.json` before the harness collected artifacts. So Kimi's exploration was sometimes stronger than its final artifact hygiene.

## Why It Beats The Baseline Mean

The key is the full mission-design objective, not just the raw capped gap. `experiments/_shared/score_normalization.py` gives revisit solutions up to 70 points for gap satisfaction. If the capped max revisit gap is at or below the expected period, the gap score saturates and the remaining 30 points come from satellite scarcity. This is a deliberate objective shape: first satisfy the revisit requirement, then reduce the constellation size needed to deliver it. In real mission architecture, meeting revisit with 8 or 12 satellites instead of 15 or 20 is not cosmetic; it is the difference between a lighter deployable architecture and a much more expensive one.

Kimi notices this two-stage objective and optimizes it. The case 0002 final reasoning explicitly says the capped gap is optimal and then treats satellite count as the remaining improvement target. The case 0005 trace is even clearer: after a valid 14-satellite 6 h solution, Kimi keeps searching because "the capped gap is already 6.0, which is the theoretical minimum" and "the secondary metric is number of satellites." That is precisely aligned with the benchmark's intended mission tradeoff. It is especially notable because the revisit floor is not actually easy for all evaluated space agents: Minimax failed every revisit case, and other successful harnesses often needed more satellites or barely matched Kimi's mean gap.

The J2 set-cover solver is more systematic and more reproducible, but its submitted architectures are conservative. Its README describes a certified J2-aware repeat-ground-track set-cover pipeline that selects confirmed candidate-target assignments and emits assigned schedules. In the main-solver rows it reliably reaches the gap floor on all five cases, but with 15-20 satellites. Kimi, by contrast, uses an opportunistic black-box search over simple constellation families and verifier-tested final artifacts. This is weaker as a principled solver but surprisingly strong at the architecture-design part of the benchmark, especially on cases where a small high-inclination or many-plane design can satisfy every target threshold.

## Why This Is Not Just Luck

There is luck in the specific phase searches, especially case 0005's random offset discovery, but the success is not accidental schema luck. Kimi repeatedly acquires the right contract, writes the required `satellites` and `actions` shape, uses SI units and GCRF states, and checks the local verifier. It also debugs concrete physical mistakes: in case 0002 it catches a meter-versus-kilometer range confusion while testing 7-satellite feasibility, and in several cases it increases safety margins after verifier-reported slant-range or geometry failures. Those are signs of a solver loop being corrected by the authoritative tool, not a private verifier overriding the benchmark.

The luck is instead search luck within a good workflow. Kimi's model is approximate and ad hoc, but the benchmark's exposed contract makes a useful approximation achievable. When a candidate passes the opaque verifier, Kimi can safely keep it. When a candidate almost passes, the verifier reveals which target and constraint are bottlenecking the score. This turns an evaluated space agent into a black-box optimizer over a compact design space.

## Failure Edges

The main weakness is artifact discipline. Kimi sometimes finds a better solution than it finally submits or preserves. Case 0004 is the cleanest example: verified 17-satellite files existed in the workspace, but `solution.json` was apparently not updated before the run ended, yielding an 18-satellite aggregate result. This looks less like reasoning failure than state-management failure: the candidate-generation loop wrote benchmark-valid side artifacts, but the final handoff path remained the canonical `solution.json`. Case 0001 appears similar in spirit: a verified 15-satellite solution at the 6 h floor was followed by a 14-satellite search that did not converge, and the final row lost the gap floor.

The second weakness is that the method is not a reusable solver yet. It is a trace-time program synthesis loop: write a solver, patch API mistakes, try constellations, run verifier, repeat. That can beat a conservative baseline on a small public split, but it is sensitive to timeout, file overwrites, stochastic search, and whether the generated script has enough physical fidelity for the case. In other words, Kimi's result is impressive as an agentic workflow, not as evidence that the produced method is more robust than the first-party solver across broader distributions.

## Takeaway

Kimi succeeds on `revisit_constellation` because this benchmark rewards a disciplined architecture-search loop: read the comprehensive README, use Brahe or a close-enough J2/geometry model to generate candidates, run the opaque verifier often, and once the capped gap hits the required revisit floor, search aggressively for fewer satellites. The result surpasses the solver baseline mean because Kimi is unusually effective at the constellation-size part of the mission tradeoff on two cases, not because it universally improves the primary revisit metric. The broader lesson is positive but bounded: when the README is precise, the verifier is cheap enough to run repeatedly, and the scoring surface combines a hard service threshold with a compact architecture variable, an evaluated space agent can act like an adaptive experimenter and occasionally beat a conservative reproduced solver.
